# arm-telegram — commanding the arm from a phone, and refusing to

Mike types `/arm storage` then `/go pick` from his phone and the arm runs the
recorded transition — inside a window he opened deliberately, refusing rather
than queueing, quoting the board's own line back, and never once opening the
serial port.

**Nothing in this package has ever run against the real board.** The bench is
disconnected. Every number below that looks like a measurement is either lifted
from an earlier bench session or labelled as a desk choice.

```
cd Software/arm-telegram && python -m pytest -q
217 passed
```

| File | What it is |
|---|---|
| `arm_link.py` | the command channel: byte-offset tail, freshness verdict, restart detection. `ArmLink` lifted from `Software/tests/motion_verify.py`. Standard library only. |
| `policy.py` | arming, TTL, the transition table, every refusal. **Pure** — no files, no sockets, no clock. |
| `bot.py` | the Telegram adapter. `urllib` long-poll, the allowlist, the token, the settle loop. The only module that holds a secret. |
| `audit.py` | append-only JSONL, one row per decision, accepts and refusals alike. |
| `voice.py` | the voice seam. `transcribe()` returns `None`. No backend, no model, no decoder. |
| `tests/fake_daemon.py` | a **model** of `hold_arm.py`'s file channel, with replies generated by a real `ArmSim`. |

## 1. Running it

Two shells. The daemon first, always — the bot refuses to start without it.

```bash
python "C:\RobotArm\Software\arm-console\hold_arm.py"
```

```bash
cd /c/RobotArm/Software/arm-telegram
export ARM_TELEGRAM_BOT_TOKEN=...            # from @BotFather. Never committed.
export ARM_TELEGRAM_ALLOWED_CHAT_IDS=4242    # comma-separated. Never committed.
export ARM_TELEGRAM_LINK_DIR=/c/RobotArm/Software/arm-console
export ARM_TELEGRAM_TTL_S=300                # optional, defaults to 300
export ARM_TELEGRAM_AUDIT=...                # optional, defaults to <link dir>/arm_telegram_audit.jsonl
python bot.py
```

It refuses to start if the token, the allowlist or the link directory is missing,
and refuses to start on a malformed allowlist rather than dropping the entry it
could not read. An allowlist quietly one id short is a bot that ignores you, and
you would debug the arm before you debugged the comma.

| Command | Effect | Needs an armed window? |
|---|---|---|
| `/arm <pose>` | open the window, declaring the pose the arm is in **now** | — |
| `/disarm` | close it. Sends nothing to the arm | — |
| `/status` | freshness verdict plus a fresh `STA` through the file channel | no |
| `/go storage` / `/go pick` | run the recorded path, phase by phase | **yes** |
| `/stop` | send `STP`, refuse everything until re-armed | no |

Everything else is refused with the accepted list, **including any message
containing a number**. Two safe poses can have an unsafe straight line between
them, and one typed number goes straight through the rule that keeps this arm
intact (`arm-poses.csv`, in capitals: *to leave a pose, reverse its own entry
path*).

## 2. What this does NOT do — read this before believing anything

**There is no emergency stop here and there cannot be one.** `/stop` sends `STP`,
which **holds with the joints still driven**. It does not remove power, cannot
know where a shaft is, cannot make the arm safe to touch, and cannot undo a move
that already happened. `EST`, `DIS` and `CLR` are refused at the choke point in
`bot._send()` — `EST` and the watchdog **detach**, and a gravity-loaded arm falls
with nobody there to catch it. **The rocker switch and the fuse are the only
stop.**

- **It cannot prove a human is at the bench.** Arming proves a message arrived
  from an allowlisted chat id at a known time and that whoever sent it asserted a
  starting pose. It does not prove somebody is standing next to the arm, that
  hands are clear of the claw, or that the phone was in a hand rather than
  face-down on a table. It is a *deliberate act with a short expiry*, which bounds
  how long a stale intention stays valid. That is all it is.
- **There is no camera check anywhere in this package.** `arm-bench-safety` §2
  requires capturing a frame and **looking at it** before commanding any joint
  after a human has reached into the arm — because that already happened here:
  Mike said "go ahead" and in the very next frame his hand was still cupped
  around the claw. Arming is a **weaker substitute** for that rule, not an equal
  one, and re-aiming the camera would not change it. At the bench, Mike performs
  that check with his eyes. The bot never does.
- **It does not know where the arm is.** Nothing in this system observes an
  output shaft. The declared pose is *your estimate*, the same contract shape as
  `ENA <j> <adopt>`, where the firmware pre-loads a pulse before attaching and
  the number is always a human's guess. Every outcome here is read off a board
  line, and **a board ack proves the firmware accepted a command and nothing
  more** — that cost a whole afternoon on D3, where the firmware provably drove a
  joint at 29.2 °/s for 3.5 s and nothing turned.
- **It cannot stop a second writer to `arm_cmd.txt`, and does not pretend to.**
  Both this and the daemon open that file `"w"`, so two writers clobber each
  other silently with no error anywhere. Run `cycle_poses.py` while a window is
  open and commands are lost — yours, or the bot's, with nothing in either log
  saying so. **One driver at a time.** This is named, not fixed; enforcing a sole
  writer would mean changing `hold_arm.py`, which is forbidden and which cannot
  be re-proven with the bench down.
- **It cannot tell a crashed daemon from a wedged one from a laptop that went to
  sleep.** All three read `STALE`, all three refuse, and the reply says which file
  was how old rather than diagnosing why.
- **There is no PID check and there cannot be one.** `hold_arm.py` writes no PID
  anywhere, so the bot cannot know whether a process is alive and must never
  claim it. It is a better signal anyway: "alive" and "working" collapse into one
  observable — *is the status file being rewritten* — and a PID can be alive while
  the loop is wedged, which is exactly what stops feeding the 4000 ms watchdog.
- **It commands no speed.** It inherits whatever `hold_arm.py` set (J1=15,
  J3=20, J4=20, J5=20 °/s). Honest consequence: a transition is nearer 30 s than
  the PRD's estimated 19 s, which lengthens exposure inside the armed window.
- **A green test suite is evidence about this package's logic and nothing else.**
  It is a model of a bot talking to a model of a daemon talking to a model of a
  firmware. No motor, no gear, no arm.

### `/stop` cannot interrupt a transition — read this before the bench run

The bot is a **single long-poll loop**. While a transition is running it is
inside the settle loop, not reading updates. A `/stop` typed mid-move therefore
sits in Telegram's queue and **is not read until the transition has already
finished**; the `STP` goes out after the move it was meant to stop. Verified
offline: a `/go pick` and a `/stop` polled together produce `motion_complete`
and *then* `STP`, 7.9 s apart.

**Plan Phase 4 Step 5 expects to send `/stop` mid-transition and watch it take
effect. That step cannot pass as written.** Expect it, and do not read the late
`STP` as the bot ignoring you.

This is reported rather than fixed. Fixing it needs a second thread reading
updates while the first dispatches — which puts **two writers on `arm_cmd.txt`
inside this one package**, the exact hazard plan finding 6 names as unfixable
from here. That is a design change, and it is Mike's call, not a Phase 3 detail.

The same mechanism has a quieter consequence: the one-move-at-a-time rule is
enforced by the loop being **busy**, not by a refusal. A second `/go` during a
transition is not refused — it is *not read yet*. Same outcome, different
mechanism, and the difference is visible at the bench as a delay.

**The stop mid-move is the rocker switch.** It always was.

### Two failure shapes worth knowing before the bench run

- **Daemon missing at startup vs. dying afterwards are different.**
  `ArmLink.__init__` raises `SystemExit` when `arm_hold.log` is absent, so a bot
  started before the daemon stops immediately with a readable message. A daemon
  that dies *while the bot is running* does not kill the bot — the verdict goes
  `STALE`, the window closes, and everything is refused until it reads `LIVE`.
- **Killing the daemon reads `STALE`, not `NO LINK`.** The three files stay on
  disk and the status file's mtime simply ages past the 15 s window. `NO LINK`
  means a file is *absent*, which in practice means the link directory is wrong.
  Both refuse, so nothing changes — but plan Phase 4 Step 1 predicts `NO LINK` for
  a killed daemon, and it will read `STALE`. Expect that at the bench.

### The allowlist is a list of **chat** ids, not user ids

A private chat's id is the user. **A group chat's id is the group** — allowlist
one and every member of that group can command the arm. Use a private chat.

## 3. Where the plan and the source disagree — findings from this phase

The plan already carries seven of these. These four are new, and the same rule
applies: **where they disagree, the source wins.**

### Finding 8 — Telegram's own queue re-introduces the exact failure PRD §6 bans

**This one changes behaviour and it is the important one.** The PRD refuses to
queue motion internally, for a stated reason: *"a queued motion command asserts
consent that has already expired."* But **Telegram holds undelivered updates for
about 24 hours** and replays them on the first `getUpdates`.

So: you type `/arm storage` and `/go pick` at the bench. The bot is not running.
You walk away. Tomorrow the bot starts, receives both, arms against **today's**
clock — the TTL is measured from delivery, not from when you sent it — and runs
the transition. The arm moves for consent that expired yesterday, with nobody in
the room. Refusing to queue internally does nothing about a queue somebody else
is holding.

**Resolution:** `Bot.drain_backlog()` runs before the first real poll:
`getUpdates(offset=-1, timeout=0)`, take the highest `update_id`, skip past it,
and write an audit row saying so. Nothing in a backlog is ever read as a command.
Asserted by `test_a_startup_backlog_is_discarded_and_never_replayed`.

Neither the PRD nor the plan mentions this. **PRD §15's invariant list should gain
a line**, and that is Mike's call, not mine.

### Finding 9 — the bot needs two clocks, and mixing them is a real bug

`link.observe(now)` compares `now` against `arm_status.txt`'s **mtime**, so it
needs **wall** time. `policy.decide(now)` measures a TTL, so it needs a
**monotonic** clock a sleeping laptop or an NTP step cannot move backwards. Pass
`time.monotonic()` to `observe()` and it reports a status file aged by the whole
uptime of the machine and refuses everything; pass `time.time()` to `decide()` and
the arming window belongs to the system clock. Both are injected in `bot.py`,
which is also what makes the TTL testable with a number instead of a five-minute
sleep.

### Finding 10 — a settle timeout must send nothing, and that had to be chosen

The plan does not say what happens when a phase never reaches its commanded
angles. The instinct is to "make it safe", and **on this arm there is no such
command**. So a settle timeout does exactly what expiry does: the bot goes quiet,
voids the declared pose, closes the window, and tells you the arm may be part-way
along the path. It does **not** send `STP` on its own — that would be this layer
deciding, unprompted, to command an arm that is somewhere nobody knows. `/stop`
is one message away and works unarmed.

The timeout is **25 s per phase**, a **desk choice**: the bot commands no `SPD`
so it cannot compute a travel time. The arithmetic behind the number is in
`bot.SETTLE_TIMEOUT_S`. The settle *predicate* is not a choice — it is
`cycle_poses.settle()`'s, unchanged (`MOV=0` **and** `SET == target`), at its
0.12 s interval, because that is the one that ran 16 clean cycles.

### Finding 11 — `ArmLink.send()` raises `SystemExit`, which is not an `Exception`

**This one would have killed the bot in the field.** `ArmLink.send()` raises
`SystemExit` when the daemon never logs a reply — lifted verbatim from
`motion_verify.py`, a command-line script, where exiting is exactly right.
`SystemExit` inherits from `BaseException`, so a plain `except Exception`
catch-all **does not catch it**. A single unanswered command, possibly
mid-transition, would have taken the whole bot process down: no reply, no audit
row, no explanation. The arm stays held by the daemon so nothing falls — the
operator is simply left with a phone that stopped answering.

Two bugs at once, because the state was also left with `in_flight` set, so every
later `/go` **and every `/arm`** refused `move_in_flight` for ever. Only `/stop`
cleared it, and nothing said so.

**Resolution:** `handle_update` catches `(Exception, SystemExit)` — not
`BaseException`, which would swallow Ctrl-C — voids the state outright, audits,
and replies. Fixed in `bot.py` and **not** in `arm_link.py`: that copy has to go
on behaving exactly like `motion_verify.ArmLink` or the Phase 1 drift guard stops
meaning anything. The bot is what has to be robust.

### Finding 12 — an `ast` guard for the forbidden verbs cannot work

A scan for a string literal beginning `EST` / `DIS` / `CLR` was written and it
failed immediately — on `policy.py`'s own `FORBIDDEN_VERBS = ("EST", "DIS",
"CLR")`, the constant that **enforces** the rule. A text scan cannot tell a
denylist from a command, so it would need an exemption for the one file most
worth checking. It was deleted. The enforcement is runtime instead:
`bot._send()` is the single choke point for every line this package writes —
including the `STA` the settle loop invents, which `policy._guard()` never sees —
and the tests assert on the lines that actually reached the daemon.

## 4. Still Mike's call, and nothing here decides them

1. **The TTL.** 300 s ships because the PRD recommends five minutes (Q17-Q3,
   unanswered). It is one env var. **It is your number, not a tuning default.**
2. **The speed.** The PRD proposed commanding `SPD 25`; the daemon currently holds
   the arm at 15–20 °/s, so the phone would be **speeding the arm up, not slowing
   it down**. This bot therefore commands no speed at all. Plain English: *right
   now the arm moves at whatever speed the holder program set, and the phone does
   not change it.* Raising it is a bench decision.
3. **The voice backend.** None chosen (Q17-Q1). Any dependency it needs gets a
   written licence note, with its licence named, **before** it is installed —
   Apache-2.0 or MIT only. That is a stop-and-ask.
4. **Two stale lines in `arm-serial-control`.** §4 tells the next person to
   `from motion_verify import ArmLink`, which now drags OpenCV into any process
   that follows it — that instruction is why `arm_link.py` is a lifted copy. §10
   says `hold_arm.py` "is not committed"; it is, at
   `Software/arm-console/hold_arm.py`. Correcting a skill is your call.

## 5. Where I was wrong while building this

Kept because each was nearly shipped as fact.

1. **The token tests passed with token-scrubbing deleted.** The suite went green,
   55 tests, with `_reply`'s scrub removed — because every test that mentioned the
   token fed it text some earlier layer had *already* scrubbed. "Two layers on the
   one secret" was a sentence in a docstring, not a fact. Found by deliberately
   breaking the code and re-running, not by reading it. Two tests now assert each
   layer **on its own**, and the same probe against `audit.py` closed the matching
   hole there. **A test that mentions the thing is not a test of the thing.**
2. **I nearly shipped a bot that a single unanswered command would kill.**
   `except Exception` does not catch `SystemExit`, and `ArmLink.send()` raises
   one (finding 11). Found by probing the failure after a review asked whether
   the state could wedge — not by reading the code, which I had read twice.
   **The exception you did not think to raise is the one that escapes.**
3. **I nearly shipped the `ast` forbidden-verb guard** (finding 12) — it would
   have needed an exemption for `policy.py`, and an exempted guard reads as
   coverage while proving nothing.
4. **I assumed a settle timeout would want to send `STP`.** It is the same
   instinct the PRD names as the trap in §5a, one layer down.

## 6. Do not

- ❌ Treat a green run here as evidence about the physical arm. It is evidence
  about this package's logic and nothing else.
- ❌ Call `/stop` an emergency stop, in code or in copy. Nothing here is one.
- ❌ Add `EST`, `DIS`, `CLR`, or any verb outside `policy.ALLOWED_VERBS`.
- ❌ Import `serial`, name the serial port, or add a "just to check" port open.
  `tests/test_no_serial.py` fails loud, including if a rename empties its glob.
- ❌ Add a dependency. Standard library only — that is the strongest true
  statement this package has.
- ❌ Fuzzy-match a transcription to the nearest pose name. "pick", "quick" and
  "stick" are one bad microphone apart.
- ❌ Report a move's outcome from `arm_status.txt`. It is rewritten on the 5 s
  poll, so right after a `MOV` it still holds pre-move state — and says `MOV=0`.
- ❌ Poll the link faster than 0.12 s.
- ❌ Run `cycle_poses.py` while an armed window is open.
- ❌ Let the bot run unattended. Nothing holds this arm up except the daemon's
  torque, no pose is self-supporting, and if the daemon dies the arm falls while
  a status file that stopped updating still reports every joint on.
